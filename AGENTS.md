# Polyglot Code Offline Layout - Project Documentation

## Project Overview

**polyglot-code-offline-layout** calculates d3 layout data (voronoi and circle packing) for code repository visualizations. It processes JSON input files containing code tree structures and adds geometric layout information (polygons, centers, dimensions) that can be used by visualization tools.

## Usage

### Basic Usage
```bash
node layout.js -i input.json -o output.json
```

### Options
- `-i, --input`: Input JSON file path
- `-o, --output`: Output JSON file path  
- `-c, --circles`: Use circle packing for top level (boolean)
- `-n, --nested-circles`: Use nested circle packing until git repo root, then voronoi (boolean)
- `-p, --points`: Number of points in bounding polygon (default: 128)
- `-g, --goodenough`: Accept good-enough voronoi simulation (default: true)

### Layout Modes

**Three layout modes are available:**

1. **Voronoi-only** (default): `node layout.js -i input.json -o output.json`
   - Entire tree uses voronoi layout
   - All nodes sized proportionally to their value (LOC)

2. **Top-level circles** (`-c`): `node layout.js -c -i input.json -o output.json`
   - Root's children use circle packing
   - Each child's subtree uses voronoi
   - Good for visualizing top-level project structure

3. **Nested circles** (`-n`): `node layout.js -n -i input.json -o output.json`
   - Circle packing recursively applied to directory nodes
   - Switches to voronoi at git repository roots
   - Provides hierarchical visual structure matching repository organization

## Testing

```bash
npm test          # or: node test/layout.test.js
```

`test/layout.test.js` builds its own small fixtures (`test/fixtures.js`), runs
`layout.js` as a subprocess in each mode, and checks the invariants that are
easy to break silently:

- **A repo circle has area proportional to its lines of code, at the same ratio
  at every nesting depth** - the central property of the layout. Every circle
  has radius `sqrt(loc)`, so its polygon area is `polygonAreaFactor(points) * loc`.
- `-n` and `-c` produce identical repo circles when all repos are top level
- Git repo roots keep `scaleFactor` 1.0; directories grow (never shrink) to contain children
- Packed children stay inside their parent and do not overlap
- A tree that is itself a repo uses the same area:loc scale as a nested one
- A repo vendored inside another repo keeps the ratio (via voronoi area share)
- Voronoi cells tile their parent exactly
- Circle-packed nodes keep `width`/`height` after `calculateVoronoi` replaces their layout
- Files are emitted with no `children` key

## JSON Input Format

### Git Repository Root Detection

Input JSON is generated by `/polyglot-code-scanner/src/git.rs` and `/polyglot-code-scanner/src/flare.rs`.

**Git repo roots are marked as follows:**
- Directory nodes with a `.git` subdirectory will have a `data.git` field populated with `GitInfo` containing `{remote_url: string, head: string}` fields
- Files with git history will have `data.git` with different fields: `{activity, age_in_days, creation_date, details, last_update, user_count, users}`
- To detect a repo root in JavaScript: `node.data?.git && (node.data.git.remote_url || node.data.git.head)`
  - This checks for the presence of directory-specific git fields
  - Files have git data but with completely different fields (history tracking, not repo info)
- **Scanner requirements**: Must run scanner without `--no-git` flag and with `--years N` for sufficient history window

**Tree structure:**
- Root node: `name: "<root>"`, no git markers at root level
- Directories: `children` array with name/data/children
- Files: no `children` field
- Data: optional `git`, `loc`, `indentation`, `coupling`, `file_stats` fields (conditionally serialized)

## Nested Circles Algorithm

The nested circles mode uses hierarchical circle packing with the following approach:

1. **Bottom-up radius calculation**: Recursively pack children first to determine their required radii
2. **Sibling packing**: Use `d3.packSiblings()` with actual (potentially scaled) radii to position nodes
3. **Scaling**: If a node needs more space to contain its packed children than its natural radius, scale up
4. **Git boundary**: Switch from circle packing to voronoi at git repository root directories
5. **Absolute coordinates**: All positions stored in absolute (root) coordinate space for D3 visualization

Key insight: All layout coordinates are absolute positions in root space, not relative to parents. This enables direct D3 rendering without coordinate transformation.

### The area:loc invariant

Every circle has radius `sqrt(value)`, so its area is proportional to its lines
of code. When a directory cannot contain its packed children, the code grows the
*parent* rather than shrinking the children (see `calculateNestedCircles`), which
is what keeps a repo circle at the same area:loc ratio however deeply it is
nested. Inside a repo, voronoi splits the circle by loc share, so files inherit
the same ratio.

The cost is that packing slack compounds up the tree: with repos six levels deep,
the root can end up ~4x its natural radius and repo circles occupy under 10% of
the diagram, versus ~45% in `-c` mode. That is inherent to hierarchical circle
packing, not a bug.

Note that on a *voronoi* node `layout.radius` is notional (`sqrt(value)`) and does
not bound `layout.polygon`. Only circle-packed nodes - which go through
`applyCircleMetrics()` - have a radius that bounds their polygon.
